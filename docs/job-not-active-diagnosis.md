## 已确认与尚待确认

- 已确认：服务端在结算时认定任务不再处于有效状态；客户端没有 300 秒的本地任务终止规则。
- 已确认：原客户端拒绝结算后清理当前任务，约 3 秒后继续领取，能重复领取同曲的新任务 ID 并整首播放。这已在本地模拟复现。
- 待确认：服务端是否存在约 300 秒固定期限、过期扫描、按领取时间清理活跃任务，或其他任务状态变更。当前工作区只有客户端源码，尚未读取实际部署的服务端配置、数据库和日志。
- 心跳确认仅说明接口接受了该请求，不能据此断言任务已续期。旧客户端代码还将心跳标注为“纯记录不校验”，任务上限注释为 15 分钟；这些历史注释不代表当前部署规则。

## 客户端修复范围

1. 明确的 `job_not_active` / `job_expired` 结算拒绝会暂停自动领取；不自动重播、不伪报入账。网络或 5xx 错误仍沿用原有有界重试规则。
2. Docker 状态接口与页面保留暂停原因。自动重连浏览器不解除暂停；用户在设置中重新填写现有密钥并保存后恢复。该暂停状态保存在当前进程内，容器重启会重新尝试。
3. 保留服务端 `requiredListenMs` / `requiredListenRatio`，用于曲终的最低有效播放校验，不借此任意缩短歌曲播放目标。明显截短或试听音源不足要求时放弃任务。
4. 将实际有效播放时长、媒体位置和自然结束状态分开。真实观察到的倍速、跳播、回退、漂移与停滞证据随结算上报；跳到曲末不能伪装成完整播放。

以上修改解决客户端反复浪费播放和误提交的问题，**尚不能证明服务端约 300 秒后的任务失效原因已经修复**。

## 服务端需核对的证据

按上表任务 ID 查找实际状态、领取时间、任务期限、最后心跳时间、失效时间及触发状态变更的处理器。字段名称以真实服务端实现为准。随后核对：

- `/next` 下发的目标全长、最低听时要求与任务期限是否相容，是否留有正常起播、缓冲和结算请求的时间。
- 心跳处理器是仅记进度还是会续期；若仅记进度，成功响应不能代表任务仍有效。
- 定时清理和查询时清理是否使用同一过期规则，是否会清除仍在真实播放、持续有心跳的长任务。
- `/finish` 是否因任务过期、其他客户端放弃、并发领取或重复结算而返回同一个 `job_not_active`。应保留具体状态变更原因，不能直接把已失效任务改为成功。

服务端修复后需覆盖：270 秒、299 秒加数秒起播耗时、310 秒和 332 秒正常播放；并验证停止心跳后仍能过期、重试同一结算不会重复记账。完成这些验证后，才可确认这批长曲失败已根治。

## 应用与验证

运行本地 core 与 Docker 回归测试及 Docker 源码构建。测试使用本地替身或本地媒体，不代表已验证线上账号、平台播放统计或服务端结算。

本次验证结果：core 98/98 通过；Docker 182 项普通回归通过，另外指定本机 Chrome 后 4/4 本地媒体回归通过（合计 Docker 186 项）；Docker 源码构建通过。独立复查重现了 300 秒正常播放的 20/40 毫秒交替采样抖动，修复后均累计 300000 毫秒，并验证迟到的启动请求不能解除新发生的暂停。

部署需要用本次源码重新构建 `apps/docker/Dockerfile` 对应镜像，并以原数据卷重建容器；仅重启原镜像不会载入源码修复。本次未发布镜像或修改线上服务端。
